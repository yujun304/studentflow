StudentFlow 중학생 포트폴리오용 기술 난이도 낮추기 제안
==========================================================

작성 목적
---------

현재 StudentFlow는 React, FastAPI, PostgreSQL, 비동기 DB, JWT Access/Refresh Token,
CSRF, Docker, Alembic까지 포함하고 있어 일반적인 중학생 포트폴리오보다 기술 범위가 넓다.

프로젝트 폴더 구조와 이미 구현된 핵심 기능을 크게 바꾸지 않으면서도 다음 목표를 달성하는 방법을
정리한다.

1. 발표자가 실제로 이해하고 설명해야 하는 범위를 줄인다.
2. 시연 중 오류가 날 수 있는 지점을 줄인다.
3. “어려운 기술을 많이 사용했다”보다 “필요한 문제를 안정적으로 해결했다”에 집중한다.
4. 보안과 데이터 무결성을 무리하게 제거하지 않는다.
5. 현재 frontend/backend/PostgreSQL 구조는 유지한다.


가장 먼저 정할 핵심 범위
-------------------------

포트폴리오에서 다음 다섯 기능만 핵심 완성 기능으로 소개하는 것을 권장한다.

1. 관리자 계정 생성과 역할·학년 관리
2. 공지와 선착순 신청
3. 업무 배정, 제출, 승인·반려
4. 조 편성 승인 후 개인 달력 자동 반영
5. 행사 출석 체크리스트

PWA, Push, 클라우드 저장소, 아카이브, 범용 감사 로그 등은 “현재 핵심 범위”에서
제외하거나 후속 확장 계획으로만 소개한다.

이렇게 하면 전체 프로젝트 구조는 그대로 두면서 발표해야 할 기술 흐름을 절반 이하로 줄일 수 있다.


방법 1. 발표 범위만 줄이고 코드는 그대로 둔다
-----------------------------------------

난이도 감소: 매우 큼
구조 변경: 없음
추천도: 가장 높음

방법

- 포트폴리오 화면과 발표 자료에서 핵심 기능 다섯 개만 설명한다.
- Refresh Token rotation, PWA 같은 기술은 질문을 받았을 때만 짧게 답한다.
- 구현 중인 기능은 “확장 예정”으로 분리한다.
- 모든 DB 테이블을 설명하지 말고 User, Task, Submission, Team, Reminder, Event,
  Attendance 정도만 설명한다.
- 비동기 프로그래밍 원리를 깊게 설명하기보다 “DB 요청을 기다리는 동안 서버가 다른 요청을
  받을 수 있도록 async를 사용했다”고 한 문장으로 정리한다.

장점

- 코드 손상 위험이 없다.
- 이미 통과한 테스트와 동작을 그대로 유지할 수 있다.
- 질문이 들어오면 실제 구현 코드를 보여줄 수 있다.

주의점

- 자신이 설명하지 못하는 기술을 전부 직접 설계했다고 과장하면 안 된다.
- “사용한 기술”과 “이번 발표에서 집중할 기술”을 구분해야 한다.


방법 2. 역할을 네 종류에서 두 가지 대표 흐름으로 설명한다
-------------------------------------------------

난이도 감소: 큼
구조 변경: 없음
추천도: 높음

코드에는 MEMBER, DEPARTMENT_HEAD, EXECUTIVE_BOARD, TEACHER를 유지한다.
하지만 시연과 발표에서는 다음 두 사용자만 사용한다.

- 학생: 배정 업무 확인, 제출, 조 일정과 출석 기록 확인
- 관리자 선생님: 계정, 공지, 업무, 검토, 출석 관리

부장단과 회장단은 “학생과 교사 사이의 중간 관리 권한이며 부서/전체 범위가 다르다”고만 설명한다.

장점

- RBAC와 부서 범위 코드를 삭제하지 않아도 된다.
- 로그인 계정 두 개만 준비하면 시연할 수 있다.
- 권한 설명이 훨씬 짧아진다.


방법 3. 한 가지 연결 시나리오만 시연한다
-------------------------------------

난이도 감소: 매우 큼
구조 변경: 없음
추천도: 가장 높음

다음 시나리오만 외워서 시연한다.

1. 선생님이 행사를 등록한다.
2. 조 편성 업무를 학생에게 배정한다.
3. 학생이 조원과 활동 시간을 입력해 제출한다.
4. 선생님이 승인한다.
5. 조원 달력에 행사와 조 일정이 나타난다.
6. 행사 출석 체크리스트에서 출석 상태를 저장한다.

공지·선착순은 두 번째 짧은 예시로만 보여준다.

이 시나리오는 업무, 제출, 검토, 자동 일정, 행사, 출석이 연결되어 있어 기능을 많이 돌아다니지
않아도 프로젝트의 장점을 충분히 보여준다.


방법 4. 아직 준비되지 않은 API를 발표 대상에서 완전히 제외한다
------------------------------------------------------

난이도 감소: 큼
구조 변경: 매우 작음 또는 없음
추천도: 높음

현재 501 feature_not_ready를 반환하는 라우터는 포트폴리오 완성 기능으로 말하지 않는다.

선택 가능한 정리 방법

A안: 코드는 그대로 두고 메뉴와 문서에서만 숨긴다.
B안: app/main.py에서 미완성 라우터 include_router 줄만 잠시 주석 처리한다.
C안: “실험/후속 기능”이라는 별도 목록으로 분리한다.

A안이 가장 안전하다. 구조를 바꾸지 않고도 면접관이 미완성 API를 핵심 기능으로 오해하는 일을
막을 수 있다.


방법 5. 채팅 기능을 프로젝트 범위에서 제거한다
-------------------------------------------

난이도 감소: 매우 큼
구조 변경: 작음
추천도: 적용 완료

채팅은 프로젝트의 핵심인 업무·조 편성·달력·출석 흐름과 직접 연결되지 않으면서 메시지 저장,
참여자 권한, 읽음 처리와 실시간 연결까지 많은 설명이 필요했다. 현재는 API, 모델, 테스트와 DB
테이블을 제거해 핵심 도메인에 집중하도록 정리했다. 초기 기획 문서의 채팅 내용은 현재 범위에서
제외한다.


방법 6. PWA는 “설치 가능”까지만 남긴다
------------------------------------

난이도 감소: 중간
구조 변경: 없음
추천도: 높음

- 앱 설치용 manifest와 service worker 등록만 유지한다.
- 오프라인 저장, Background Sync와 실제 Push 발송은 하지 않는다.
- 발표에서는 “웹사이트를 홈 화면에 설치할 수 있는 기본 구조”라고만 설명한다.

Push 서버, VAPID 키, 브라우저 권한 흐름까지 들어가면 프로젝트의 핵심 문제와 관계없는 설명이
길어진다.


방법 7. 파일 저장은 로컬 비공개 저장소만 사용한다
--------------------------------------------

난이도 감소: 큼
구조 변경: 없음
추천도: 가장 높음

현재 STORAGE_BACKEND 설정 계약은 남기되 포트폴리오 버전은 local만 사용한다.

설명 방식

- 업로드 파일은 웹 정적 폴더가 아닌 비공개 볼륨에 저장한다.
- 다운로드 전에 서버가 사용자 권한을 검사한다.
- 실제 운영 규모가 커지면 같은 인터페이스에 S3 구현을 추가할 수 있다.

AWS 계정, 버킷 정책, presigned URL, IAM까지 구현하지 않아도 파일 보안의 핵심 개념을 보여줄 수 있다.


방법 8. 인증 설명을 세 단계로만 단순화한다
-----------------------------------------

난이도 감소: 중간
구조 변경: 없음
추천도: 높음

인증 코드를 제거하지 말고 다음 세 문장만 정확히 이해한다.

1. 로그인하면 서버가 HttpOnly 쿠키에 인증 토큰을 저장한다.
2. 중요한 변경 요청은 CSRF 토큰이 맞는지 추가로 확인한다.
3. 서버는 API를 호출할 때마다 현재 사용자 역할과 활성 상태를 확인한다.

Refresh Token digest, rotation, session_version은 추가 질문이 있을 때 설명한다.

피해야 할 단순화

- 비밀번호를 평문으로 저장하기
- JWT 비밀키를 소스 코드에 고정하기
- CSRF 검사를 제거하기
- 프론트 메뉴 숨김만으로 관리자 권한을 처리하기

이 부분을 제거하면 난이도는 낮아지지만 포트폴리오의 신뢰성과 안전성도 크게 떨어진다.


방법 9. 비동기 구조는 유지하되 직접 작성 범위를 제한한다
------------------------------------------------

난이도 감소: 중간
구조 변경: 없음
추천도: 중간 이상

FastAPI와 SQLAlchemy async 구조를 동기 방식으로 전부 바꾸는 것은 파일 대부분을 수정해야 하므로
추천하지 않는다.

대신 다음 규칙만 사용한다.

- API 함수는 async def로 작성한다.
- DB 조회에는 await를 붙인다.
- 요청 하나에서 관련 변경을 끝낸 뒤 한 번 commit한다.
- 복잡한 동시 처리를 새로 만들지 않는다.
- CPU 작업, 스레드, 이벤트 루프 내부 동작은 발표 범위에서 제외한다.

이미 작동하는 async 구조를 동기 코드로 다시 쓰는 것보다 현재 패턴을 반복해서 사용하는 편이 훨씬
안전하다.


방법 10. 서비스 계층을 더 늘리지 않는다
-----------------------------------

난이도 감소: 중간
구조 변경: 없음
추천도: 높음

현재 구조는 대부분의 흐름이 app/api에 있고, 여러 기능이 공유하는 조 편성·달력 규칙만
app/services에 있다. 여기서 Repository, Unit of Work, Domain Event, CQRS 같은 계층을 추가하지 않는다.

간단한 기준

- 한 API에서만 쓰는 로직: 해당 api 파일에 둔다.
- 둘 이상의 API가 공유하는 규칙: services에 함수로 분리한다.
- 설정, 인증, DB, 파일처럼 전체가 공유: core에 둔다.

이 정도면 폴더 역할을 쉽게 설명하면서 중복도 줄일 수 있다.


방법 11. API 요청 형식을 새 추상화 없이 유지한다
---------------------------------------------

난이도 감소: 중간
구조 변경: 없음
추천도: 높음

GraphQL, 메시지 큐, 범용 Command Bus를 추가하지 않는다.

- 조회: GET
- 등록: POST
- 일부 수정: PATCH
- 목록 전체 교체나 일괄 저장: PUT
- 삭제: DELETE

현재 REST 규칙을 그대로 유지하고, 각 요청·응답은 Pydantic 모델로 명확히 적는다.


방법 12. 자동 조 편성은 “자동 배치 알고리즘”으로 확장하지 않는다
---------------------------------------------------------

난이도 감소: 매우 큼
구조 변경: 없음
추천도: 가장 높음

현재 자동화의 의미는 담당자가 입력한 조 편성을 승인하면 대상자의 달력과 행사 명단에 자동으로
반영하는 것이다. 성별, 학년, 친밀도, 역할을 계산해 컴퓨터가 조를 나누는 최적화 알고리즘은 아니다.

포트폴리오에서도 다음처럼 정확히 표현한다.

“구조화된 조 편성 자동 반영”

피해야 할 표현

“AI 자동 조 편성”
“최적 조합 계산”

자동 배치 알고리즘을 추가하면 조건 설계, 공정성, 결과 수정, 테스트 난이도가 급격히 높아진다.


방법 13. 출석은 수동 체크리스트에 집중한다
-----------------------------------------

난이도 감소: 큼
구조 변경: 없음
추천도: 가장 높음

현재처럼 관리자가 명단을 보고 출석, 결석, 지각, 조퇴 중 하나를 선택하는 방식만 유지한다.

추가하지 않을 기능

- QR 출석
- GPS 확인
- 얼굴 인식
- 학생의 자동 출석 처리
- 실시간 위치 추적

수동 방식은 학교 현장에 맞고 개인정보 문제도 적으며, 데이터 모델과 권한 검사를 명확하게 설명할 수
있다.


방법 14. 감사 기록은 출석 변경에만 한정한다
-------------------------------------------

난이도 감소: 중간
구조 변경: 없음
추천도: 높음

모든 테이블 변경을 자동 추적하는 범용 감사 시스템을 만들지 않는다.

현재 중요한 출석 변경에 대해서만 다음 항목을 저장한다.

- 변경한 사람
- 대상 행사와 사용자
- 이전 상태
- 새 상태
- 변경 시각

감사 로그 화면과 복잡한 검색은 후속 기능으로 둔다.


방법 15. 알림은 달력 리마인더 생성까지만 구현한다
----------------------------------------------

난이도 감소: 큼
구조 변경: 없음
추천도: 높음

조 편성 승인 시 Reminder 행을 만들고 달력에 표시하는 기능을 핵심으로 둔다.

다음 기능은 확장 예정으로 둔다.

- 이메일 발송
- 문자 발송
- 실제 Web Push 발송
- 반복 알림 스케줄러
- 백그라운드 작업 큐

현재 기능도 “확정된 조 일정이 개인 화면에 자동으로 나타난다”는 사용자 가치를 충분히 보여준다.


방법 16. 통합 달력은 두 달 고정 범위로 유지한다
--------------------------------------------

난이도 감소: 중간
구조 변경: 없음
추천도: 높음

- 이번 달과 다음 달만 보여준다.
- 드래그 앤 드롭 일정 변경을 추가하지 않는다.
- 반복 일정 규칙을 추가하지 않는다.
- 외부 Google Calendar 동기화를 추가하지 않는다.
- 행사·업무 일정은 원본 기능에서만 수정한다.
- 달력에서는 개인 일정만 직접 편집한다.

이 규칙은 일정 원본이 어디인지 명확하게 유지해 데이터 동기화 문제를 줄인다.


방법 17. Docker 사용법을 한 명령으로 고정한다
------------------------------------------

난이도 감소: 큼
구조 변경: 없음
추천도: 가장 높음

발표와 제출 환경에서는 다음 한 가지 실행법만 사용한다.

docker compose up -d --build

개별 PostgreSQL 설치, 백엔드 로컬 실행, 프론트 개발 서버 실행은 개발 중에만 사용한다.

시연 전 확인할 것은 다음 세 가지뿐이다.

1. Docker Desktop 실행 여부
2. http://localhost:8081 접속 여부
3. 테스트 계정 로그인 여부

Kubernetes, AWS ECS, CI/CD 자동 배포는 현재 포트폴리오 범위에서 제외한다.


방법 18. 테스트는 핵심 사용자 흐름 중심으로 제한한다
-----------------------------------------------

난이도 감소: 중간
구조 변경: 없음
추천도: 높음

모든 함수의 세부 구현을 테스트하려 하지 말고 다음 흐름을 우선한다.

- 로그인과 CSRF
- 공지 수신자와 선착순 정원
- 업무 배정과 제출 최신 버전
- 조 편성 승인 후 리마인더 생성
- 행사 출석 일괄 저장
- 권한 없는 사용자 거절

설명하기 쉬운 기준

“사용자가 실제로 수행하는 중요한 흐름과 데이터가 깨지면 안 되는 부분을 테스트했습니다.”

테스트 개수 자체를 성과처럼 강조할 필요는 없다.


방법 19. 데이터베이스 설명을 관계 여섯 개로 줄인다
-----------------------------------------------

난이도 감소: 큼
구조 변경: 없음
추천도: 높음

면접에서는 다음 관계만 그림으로 설명한다.

User ─ TaskAssignee ─ Task
Task ─ Submission ─ SubmissionVersion
Task ─ Team ─ TeamMember ─ User
Team ─ Reminder ─ User
Event ─ EventParticipant ─ User
Event ─ Attendance ─ User

나머지 테이블은 질문이 있을 때 보여준다.


방법 20. DB 마이그레이션은 “스키마 버전 관리”로만 설명한다
-------------------------------------------------------

난이도 감소: 중간
구조 변경: 없음
추천도: 높음

Alembic 내부 원리를 깊게 설명할 필요는 없다.

설명 예시

“운영 데이터는 유지하면서 새 컬럼과 제약 조건을 순서대로 적용하기 위해 Alembic으로 DB 변경 이력을
관리했습니다.”

직접 설명할 마이그레이션 예시는 다음 두 개면 충분하다.

- 조 편성·달력 필드 추가
- 사용자 학년 필드와 1~3 범위 제약 추가


방법 21. 프론트 상태 관리는 React 기본 훅으로 제한한다
------------------------------------------------

난이도 감소: 중간
구조 변경: 없음
추천도: 높음

Redux, Zustand 같은 전역 상태 라이브러리를 추가하지 않는다.

- 서버 데이터: 공통 useApiData 훅
- 폼 입력과 열림 상태: React useState
- 페이지 이동: 화면별 HTML을 다시 요청하는 Vite MPA

변경 성공 후에는 현재 문서를 다시 불러온다. 이 세 규칙이면 현재 규모에서 충분하며
캐시 무효화나 Query Key를 배우지 않아도 상태의 위치를 쉽게 설명할 수 있다.


방법 22. 디자인 시스템을 새로 만들지 않는다
---------------------------------------

난이도 감소: 중간
구조 변경: 없음
추천도: 높음

현재 CSS의 panel, card, badge, actions, form-grid 같은 공통 클래스만 재사용한다.

추가하지 않을 것

- 복잡한 UI 프레임워크 교체
- 애니메이션 라이브러리
- 테마 엔진
- 다크 모드 상태 관리
- 별도 디자인 토큰 패키지

Notion과 비슷한 단순한 흰색·회색 UI 방향을 유지한다.


방법 23. 오류 메시지는 한 가지 공통 형식만 사용한다
---------------------------------------------

난이도 감소: 중간
구조 변경: 매우 작음
추천도: 높음

백엔드 오류는 다음 구조를 유지한다.

code: 프로그램이 구분하는 오류 코드
detail: 사용자가 읽는 한국어 설명
fields: 입력 검증 상세

프론트는 detail을 표시한다. 별도 국제화 시스템이나 복잡한 오류 클래스 계층은 추가하지 않는다.


방법 24. 데모 데이터와 계정을 미리 준비한다
-----------------------------------------

난이도 감소: 매우 큼
구조 변경: 없음
추천도: 가장 높음

시연 직전에 즉석에서 여러 계정을 만들면 입력 실수가 발생하기 쉽다.

권장 데모 데이터

- 교사 계정 1개
- 1학년 학생 1개
- 2학년 학생 1개
- 행사 1개
- 조 편성 업무 1개
- 일반 공지 1개
- 선착순 공지 1개

단, 실제 비밀번호나 JWT_SECRET을 포트폴리오 문서와 공개 저장소에 올리지 않는다.


방법 25. README와 면접 문서에서 완성/예정 표시를 통일한다
-----------------------------------------------------

난이도 감소: 큼
구조 변경: 없음
추천도: 높음

각 기능을 다음 세 상태로만 표시한다.

- 완료: 화면과 API가 연결되고 검증됨
- API 완료: 백엔드는 동작하지만 전용 화면이 없음
- 예정: 모델 또는 계약만 있고 실제 동작하지 않음

예시

- 조 편성 자동 달력 반영: 완료
- 출석 체크리스트: API 완료
- 실제 Push 알림: 예정
- 범용 감사 로그 조회: 예정

이렇게 하면 면접관이 프로젝트 완성도를 오해하지 않고 발표자도 답변 범위를 명확히 정할 수 있다.


난이도 감소 조합 제안
---------------------

조합 A. 코드 변경이 거의 없는 가장 안전한 방법

- 방법 1: 발표 범위 축소
- 방법 2: 학생/교사 두 역할만 시연
- 방법 3: 하나의 연결 시나리오
- 방법 4: 미완성 기능 문서에서 분리
- 방법 24: 데모 데이터 준비
- 방법 25: 완료 상태 표시 통일

예상 효과

코드는 그대로 유지하면서 설명 난이도를 약 50~60% 줄일 수 있다.


조합 B. 중학생 포트폴리오에 가장 추천하는 구성

- 핵심 기능: 계정, 공지·선착순, 업무·제출, 조 편성·달력, 출석
- 역할 설명: 학생과 교사 중심
- 파일: 로컬 비공개 저장소만 사용
- 알림: 앱 내부 달력 리마인더만 사용
- 채팅: 프로젝트 범위에서 제외
- PWA: 설치 가능 수준만 소개
- 배포: Docker Compose 한 명령
- 테스트: 핵심 흐름만 설명

예상 효과

프로젝트의 장점은 유지하면서 고등학생·대학생 수준으로 보일 수 있는 불필요한 인프라 설명을 크게
줄일 수 있다.


조합 C. 코드까지 조금 정리하는 방법

- 미완성 라우터를 main.py에서 제외
- 프론트 “더보기”의 준비 중 기능을 숨김
- 미완성 메뉴를 숨김
- README의 기술 스택을 핵심/확장으로 분리
- 사용하지 않는 스키마와 501 계약은 별도 브랜치에 보존

예상 효과

코드를 처음 보는 사람이 완성 범위를 더 빨리 파악할 수 있다.

주의

삭제 전에는 반드시 별도 Git 커밋이나 브랜치로 보존해야 한다. 현재 구조를 크게 바꾸지 않으려면
조합 A 또는 B가 더 적합하다.


추천하지 않는 난이도 낮추기
---------------------------

다음 방법은 쉬워 보이지만 프로젝트 품질을 크게 떨어뜨리거나 변경 범위가 너무 크므로 추천하지 않는다.

1. PostgreSQL을 JSON 파일로 교체
   관계와 동시성, 출석·선착순 무결성을 잃는다.

2. 백엔드 권한 검사를 삭제하고 프론트 메뉴만 숨김
   URL을 직접 호출하면 다른 사용자의 데이터를 바꿀 수 있다.

3. 비밀번호 평문 저장
   포트폴리오에서 치명적인 보안 문제로 평가될 수 있다.

4. async 코드를 전부 sync로 재작성
   얻는 효과에 비해 변경 파일과 회귀 위험이 너무 크다.

5. FastAPI를 Firebase나 Supabase로 전면 교체
   프로젝트 구조가 완전히 바뀌고 지금까지 만든 권한·검토 흐름을 다시 구현해야 한다.

6. 모든 기능을 한 파일로 합치기
   처음에는 쉬워 보여도 수정과 오류 추적이 더 어려워진다.

7. 테스트를 모두 삭제
   시연 직전 변경으로 기존 기능이 깨졌는지 확인할 수 없다.

8. 실제 구현되지 않은 기능을 완성했다고 발표
   후속 질문에서 설명할 수 없어 신뢰를 잃기 쉽다.


최종 권장안
-----------

현재 코드 구조는 바꾸지 않는다.

포트폴리오 핵심을 다음 문장으로 고정한다.

“학생회에서 업무를 배정하고 제출·검토한 뒤, 확정된 조와 행사 일정을 학생 개인 달력 및 출석
명단에 자동으로 연결하는 서비스”

발표에서는 학생과 교사 두 계정만 사용하고, 조 편성 승인부터 출석 체크까지 하나의 흐름을 보여준다.
공지·선착순은 보조 사례로 사용한다. PWA, Push, S3, 아카이브와 범용 감사 시스템은 확장
계획으로 분리한다.

이 방법은 프로젝트의 실제 장점과 현재 테스트 결과를 유지하면서도 중학생이 이해하고 설명해야 하는
기술 난이도를 가장 크게 낮춘다.


실행 순서 제안
-------------

1단계: 코드 변경 없이 발표 범위와 핵심 문장을 확정한다.
2단계: README에 완료/API 완료/예정 상태를 표시한다.
3단계: 교사·학생 데모 계정과 행사 한 건을 준비한다.
4단계: 5분 시연 순서를 반복 연습한다.
5단계: 보안, 선착순, 자동 조 편성 질문 답변만 준비한다.
6단계: 그래도 복잡하면 미완성 메뉴만 UI에서 숨긴다.

가장 중요한 기준은 기술 수가 아니라 발표자가 “왜 만들었고, 데이터가 어떻게 이동하며, 어떤 오류를
막았는지”를 자신의 말로 설명할 수 있는가이다.

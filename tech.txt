1. Codex의 역할

너는 StudentFlow 프로젝트를 설계하고 구현하는 시니어 풀스택 개발자다.

작업을 시작하기 전에 반드시 현재 저장소의 폴더 구조, 기존 코드, 설치된 라이브러리, 환경 변수, 데이터베이스 설정을 먼저 확인하라.

기존 코드를 읽지 않은 상태에서 프로젝트를 새로 덮어쓰거나, 사용자가 작성한 코드를 불필요하게 삭제하지 마라.

한 번에 전체 기능을 구현하지 말고, 단계별로 구현한 뒤 각 단계마다 다음 내용을 보고하라.

2. 프로젝트 개요

프로젝트명은 StudentFlow다.

StudentFlow는 중학생 학생회의 활동을 관리하기 위한 폐쇄형 운영 플랫폼이다.

학생회 구성원과 담당 선생님만 로그인하여 사용할 수 있으며, 공개 회원가입은 제공하지 않는다.

학생회에서는 행사, 캠페인, 업무 제출, 조 편성, 출석 확인, 회의, 공지, 채팅 등 다양한 활동이 이루어진다.

기존에는 이러한 정보가 메신저, 밴드, 문서 파일, 종이 명단 등에 흩어져 있어 다음과 같은 문제가 발생한다.

공지나 중요한 메시지를 놓친다.

자신이 해야 할 일을 잊는다.

업무 담당자와 마감일을 다시 확인해야 한다.

누가 제출했고 누가 제출하지 않았는지 확인하기 어렵다.

행사별 출석 기록이 체계적으로 남지 않는다.

회의록과 녹음 파일을 찾기 어렵다.

연도가 바뀌면 이전 학생회 자료가 정리되지 않는다.

StudentFlow는 소통, 업무, 일정, 제출, 출석, 기록을 하나의 서비스 안에서 연결하여 이러한 문제를 해결한다.

3. 프로젝트 모토

StudentFlow의 핵심 모토는 다음과 같다.

중학생의 특성을 반영한 유연성과 효율성

학생회 업무를 지나치게 엄격한 절차로 강제하지 않는다.

사용자는 상황에 따라 담당자, 일정, 조 편성, 업무 상태를 쉽게 변경할 수 있어야 한다.

동시에 공지, 메시지, 마감일, 준비물처럼 쉽게 잊을 수 있는 항목은 대시보드와 알림을 통해 반복적으로 확인할 수 있어야 한다.

StudentFlow는 학생들을 통제하는 시스템이 아니라, 학생들이 자유롭게 소통하면서도 해야 할 일을 놓치지 않도록 돕는 시스템이다.

5. 사용하지 않을 기술과 기능

Celery, RabbitMQ 등의 별도 메시지 큐를 기본 구성에 추가하지 마라.

8. 로그인과 접근 제어

로그인하지 않은 사용자는 내부 페이지와 내부 API에 접근할 수 없어야 한다.

공개 회원가입은 만들지 않는다.

계정은 담당 선생님 또는 권한이 있는 관리자가 생성한다.

JWT는 사용자 인증에 사용한다.

실제 권한 판단은 JWT에 들어 있는 역할 정보만으로 처리하지 않는다.

백엔드는 현재 사용자를 데이터베이스에서 확인하여 다음 항목을 검사해야 한다.

사용자가 활성 상태인지

현재 역할이 무엇인지

어느 부서에 소속되어 있는지

어떤 행사의 관리자인지

현재 기수의 구성원인지

프론트엔드에서 메뉴를 숨기는 것만으로 권한을 보호하지 않는다.

모든 보호 API에서 백엔드 권한 검사를 수행한다.

11. 업무 관리

업무는 상황에 따라 여러 형태로 사용할 수 있어야 한다.

간단 업무

내용, 담당자, 마감일만 지정한다.

담당자가 진행 중 또는 완료 상태로 변경한다.

파일 제출과 승인 절차는 필수가 아니다.

제출 업무

담당자가 파일이나 내용을 제출한다.

관리자가 승인하거나 반려한다.

공동 업무

여러 명이 함께 진행한다.

공동 담당자들이 진행 상태와 파일을 확인할 수 있다.

반복 업무

정기 회의 준비, 학생회실 정리 등의 업무를 반복 생성할 수 있도록 확장 가능한 구조로 만든다.

기본 업무 상태는 다음과 같다.

해야 할 일

진행 중

검토 중

완료

반려

업무 상태는 목록과 칸반 보드에서 확인할 수 있어야 한다.

데스크톱에서는 드래그 방식으로 상태를 변경할 수 있다.

모바일에서는 상태 선택 버튼도 함께 제공한다.

업무에 담당자, 마감일, 설명, 첨부파일, 댓글을 연결할 수 있다.

업무 절차를 지나치게 강제하지 말고, 관리자가 필요에 따라 단순 업무 또는 승인 업무를 선택할 수 있게 한다.

12. 제출물 관리

승인

반려

제출물을 수정할 때 기존 파일을 덮어쓰지 않는다.

이전 제출 내역을 버전으로 보관한다.

관리자는 제출물을 승인하거나 반려할 수 있다.

반려하는 경우 반려 사유를 작성한다.

승인 또는 반려 결과는 제출자에게 알림으로 전달한다.

제출물에는 댓글 Thread를 제공한다.

수정 요청과 답변은 일반 채팅이 아니라 해당 제출물의 댓글에서 이어갈 수 있어야 한다.

조 편성이 생성되거나 변경되면 해당 조원들의 대시보드와 행사 화면에 자동으로 반영한다.

필요한 경우 해당 조원들로 그룹 채팅방을 생성할 수 있다.

자동 생성 여부는 관리자가 선택할 수 있게 한다.

정원이 모두 찬 경우 다음 중 하나로 처리한다.

추가 신청 차단

대기자 등록

동시에 여러 사용자가 신청하더라도 최대 인원을 초과하지 않도록 PostgreSQL 트랜잭션을 사용한다.

같은 사용자가 중복 신청할 수 없게 한다.

신청자가 취소하면 가장 먼저 등록된 대기자를 자동으로 참여자로 변경할 수 있다.

대기자 승급 결과는 앱 내부 알림과 푸시 알림으로 전달한다.

20. SSE 기반 채팅 구조

웹소켓은 사용하지 않는다.

실시간 메시지 수신은 Server-Sent Events 방식으로 구현한다.

채팅 메시지 전송은 일반 HTTP POST 요청으로 처리한다.

채팅 메시지 수신은 SSE 연결로 처리한다.

기본 흐름은 다음과 같다.

사용자가 채팅방을 연다.

프론트엔드는 해당 채팅방의 기존 메시지를 일반 API로 불러온다.

프론트엔드는 SSE 스트림에 연결한다.

새 메시지가 생성되면 서버가 해당 사용자에게 SSE 이벤트를 전송한다.

사용자가 메시지를 보낼 때는 POST API를 호출한다.

전송된 메시지는 PostgreSQL에 저장된다.

저장 완료 후 관련 사용자들의 SSE 연결로 새 메시지를 전달한다.

SSE 연결이 끊기면 프론트엔드에서 자동 재연결한다.

재연결 과정에서 메시지가 빠지지 않도록 마지막으로 받은 이벤트 또는 메시지 식별자를 사용할 수 있는 구조를 만든다.

SSE 연결은 인증된 사용자만 열 수 있어야 한다.

SSE 연결 시 사용자가 접근할 수 있는 채팅방의 이벤트만 전달한다.

다른 부서나 참여하지 않은 그룹 채팅의 메시지를 받을 수 없어야 한다.

연결 유지를 위해 일정 간격으로 heartbeat 이벤트를 보낼 수 있다.

SSE 응답이 중간 프록시에서 버퍼링되지 않도록 배포 설정을 고려한다.

SSE는 서버에서 클라이언트로 전달되는 단방향 통신이라는 점을 유지한다.

메시지 작성, 수정, 삭제, 읽음 처리는 일반 REST API로 구현한다.

22. 채팅과 업무의 연결

StudentFlow의 채팅은 단순한 메신저 기능에서 끝나면 안 된다.

채팅에서 나온 중요한 내용을 실제 업무로 연결할 수 있어야 한다.

메시지를 업무로 전환

메시지 메뉴에서 업무로 등록을 선택한다.

업무 제목, 담당자, 마감일을 추가한다.

원본 메시지와 생성된 업무를 서로 연결한다.

메시지를 공지로 전환

부장단, 회장단 또는 선생님은 중요한 메시지를 공지로 전환할 수 있다.

공지 대상과 중요도를 선택한 뒤 등록한다.

메시지를 리마인더로 전환

사용자는 특정 메시지를 자신만의 리마인더로 저장할 수 있다.

다시 확인할 날짜와 시간을 지정한다.

메시지를 나중에 보기로 저장

중요하지만 바로 처리하기 어려운 메시지를 개인 목록에 저장한다.

이 기능들은 대화 속에서 나온 해야 할 일이 묻히는 문제를 해결하기 위한 핵심 차별점이다.

채팅 화면은 모바일에서 입력창이 항상 쉽게 접근 가능해야 한다.

출석 화면은 한 손으로 상태를 빠르게 선택할 수 있어야 한다.

로딩, 빈 목록, 오류, 네트워크 연결 실패, 권한 없음 상태를 각각 표시한다.

35. 보안 요구사항

비밀번호를 평문으로 저장하지 않는다.

JWT 비밀키를 코드에 작성하지 않는다.

AWS 키 또는 클라우드 저장소 키를 코드에 작성하지 않는다.

환경 변수 파일의 실제 비밀값을 저장소에 커밋하지 않는다.

모든 보호 API에서 인증과 권한을 확인한다.

공지와 채팅에 사용자가 입력한 HTML을 그대로 렌더링하지 않는다.

React의 dangerouslySetInnerHTML 사용을 피한다.

파일 업로드 시 파일 크기와 형식을 검사한다.

사용자가 파일 저장 경로를 직접 지정하지 못하게 한다.

권한 없는 사용자가 다른 사용자의 개인 채팅이나 파일에 접근할 수 없어야 한다.

SSE 연결에서도 사용자 권한을 확인한다.

사용자가 참여하지 않은 채팅방의 이벤트를 받을 수 없어야 한다.

사용자 비활성화, 비밀번호 변경, 역할 변경 시 기존 로그인 세션을 폐기할 수 있어야 한다.

중요한 관리자 작업은 변경 기록에 남긴다.

38. 테스트 필수 항목

로그인하지 않은 사용자가 내부 API에 접근할 수 없는지 확인한다.

일반 임원이 관리자 기능을 사용할 수 없는지 확인한다.

부장단이 다른 부서의 데이터를 임의로 수정할 수 없는지 확인한다.

비활성화된 사용자가 로그인하거나 SSE 연결을 유지할 수 없는지 확인한다.

선착순 신청자가 정원을 초과하지 않는지 확인한다.

같은 사용자가 중복 신청할 수 없는지 확인한다.

사용자가 자신이 참여하지 않은 채팅방을 조회할 수 없는지 확인한다.

사용자가 자신이 참여하지 않은 채팅방의 SSE 이벤트를 받을 수 없는지 확인한다.

SSE 연결이 끊어진 후 재연결되었을 때 메시지가 누락되지 않는지 확인한다.

메시지 전송은 성공했지만 SSE 연결이 끊긴 경우에도 새로 조회하면 메시지가 정상적으로 나타나는지 확인한다.

권한 없는 사용자가 클라우드 파일 다운로드 주소를 받을 수 없는지 확인한다.

출석 일괄 저장이 정상적으로 처리되는지 확인한다.

사용자가 다른 사람의 개인 리마인더를 볼 수 없는지 확인한다.

이전 기수의 데이터가 일반 사용자에게 읽기 전용으로 표시되는지 확인한다.

모바일과 노트북에서 주요 화면이 정상적으로 표시되는지 확인한다.

40. 완료 기준

다음 조건을 만족하면 1차 프로젝트가 완료된 것으로 본다.

학생회 구성원만 로그인할 수 있다.

네 가지 역할이 백엔드 권한으로 구분된다.

현재 기수와 이전 기수를 분리할 수 있다.

이전 기수 데이터가 아카이브에 보관된다.

행사와 캠페인을 생성하고 참여자를 지정할 수 있다.

업무를 배정하고 칸반 형태로 관리할 수 있다.

파일을 제출하고 승인 또는 반려할 수 있다.

조 편성이 조원들에게 자동으로 공유된다.

공지를 작성하고 읽음 여부를 확인할 수 있다.

선착순 신청이 정원을 초과하지 않는다.

날짜와 시간 변경 요청을 처리할 수 있다.

관리자가 참여자의 출석 상태를 기록할 수 있다.

회의록과 녹음 파일을 업로드하고 재생할 수 있다.

전체, 부서, 그룹, 개인 채팅을 사용할 수 있다.

여러 명에게 같은 내용을 전송할 수 있다.

채팅 메시지를 POST 요청으로 전송할 수 있다.

새 메시지를 SSE 방식으로 수신할 수 있다.

웹소켓을 사용하지 않는다.

공지, 업무, 제출물, 회의록에 댓글 Thread를 사용할 수 있다.

메시지를 업무, 공지 또는 리마인더로 전환할 수 있다.

개인 메모와 리마인더를 사용할 수 있다.

권한이 있는 사용자만 클라우드 파일을 다운로드할 수 있다.

스마트폰과 노트북에서 사용할 수 있다.

PWA로 설치할 수 있다.

사용자가 허용하면 푸시 알림을 받을 수 있다.

오프라인 데이터 저장 기능은 구현되어 있지 않다.

핵심 권한, 채팅, SSE, 파일, 선착순 신청 테스트가 통과한다.
